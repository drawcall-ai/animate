# High-level authoring, scripting, and specification of character motion (state as of November 2026)

Reading conventions: **[H]** = historical/foundational (pre-2018), **[E]** = established modern (2018–2024), **[C]** = current (2025–2026). "Verified" means I read the primary text in this session; "search-level" means the claim rests on a search-result summary of the primary source and the exact wording was not checked. Quantities are quoted with the units used by the source.

## 1. Controller composition and scripting in physics-based animation (FSMs, pose-control graphs, composable controllers, control graphs, behaviour trees, skills with pre/post-conditions)

### Takeaway
The dominant, 30-year-old pattern is a *phase state machine whose states hold control laws or target poses and whose transitions fire on physical events (foot contact, loss of contact) or elapsed time* — exactly the shape of a generator "story" that issues intents and yields wait-conditions. What the strongest prior art adds, and a plain generator lacks, is an explicit contract per skill — **pre-conditions, post-conditions, and a continuously evaluated "expected performance" predicate that detects failure early and hands control to a recovery controller** (Faloutsos et al. 2001) — plus re-evaluation of conditions every tick (behaviour trees) instead of only at the current `yield`.

### Cited Findings

**Hand-authored phase state machines [H]**
- Hodgins, Wooten, Brogan & O'Brien, "Animating Human Athletics", SIGGRAPH 1995 (pp. 71–78): control algorithms for running, bicycling and vaulting are built from a shared toolbox; "state machines are used to enforce a correspondence between the phase of the behavior and the active control laws"; joints use PD servos, inverse kinematics places feet/hands, and the user specifies high-level targets such as desired velocity and facing direction (search-level) — [CMU RI PDF](https://www.ri.cmu.edu/pub_files/pub4/hodgins_jessica_k_1995_1/hodgins_jessica_k_1995_1.pdf); [SIGGRAPH archive](https://history.siggraph.org/?p=118721)
- A UW course deck derived from the paper shows the running state machine advancing through stages such as heel contact, loading and unloading with transitions triggered by events like the ball of the foot touching or leaving the ground (secondary source; state names should be checked against the paper) — [UW CSE457 lecture](https://courses.cs.washington.edu/courses/cse457/01au/lectures/realistic-character-animation.pdf)
- SIMBICON (Yin, Loken & van de Panne, SIGGRAPH 2007, ACM TOG 26(3)): a controller is a finite state machine in which each state holds a target pose tracked by PD control; there are two transition types — after a fixed elapsed time, or on foot contact; if the contact has already occurred when a contact-exit state is entered, that state is skipped; target poses are frequently *not reached* (e.g. the swing leg is commanded backward so that it swings down into contact) — i.e. the pose is an intent, not a keyframe; balance comes from continuously modifying the swing-hip target by linear feedback on centre-of-mass position and velocity relative to the stance foot (search-level reading of the paper) — [paper PDF](https://www.cs.ubc.ca/~van/papers/2007-siggraph-simbicon.pdf); [project page](https://www.cs.ubc.ca/~van/papers/Simbicon.htm)

**Composable controllers with explicit contracts [H] (verified from the paper text)**
- Faloutsos, van de Panne & Terzopoulos, "Composable Controllers for Physics-Based Character Animation", SIGGRAPH 2001 (pp. 251–260): any controller can join a pool managed by a *supervisor controller* provided it can answer queries about whether it can handle the current state and whether it has failed. The paper calls the explicit model of pre-conditions its key technical contribution — [paper PDF](https://www.cs.ubc.ca/~van/papers/2001-siggraph-composable.pdf)
- Definitions: "Pre-conditions are a set of conditions over the state of the character and the environment. If these conditions are met then the controller can operate"; post-conditions "define a range of states for the final state of the character after the execution of the controller" — the controller "realizes a mapping between a domain of input states to a range of output states"; *expected performance* lets a controller "evaluate its performance in order to detect failure at any point during its operation" — [paper PDF](https://www.cs.ubc.ca/~van/papers/2001-siggraph-composable.pdf)
- Failure semantics: "Failure in our case means that the controller cannot meet its post-conditions"; "The sooner a controller can detect failure the sooner another more appropriate controller can take over ... the character should not attempt to continue a walking gait if it has lost its balance and it is falling." Expected performance E is expressed with the same kind of predicates as pre-conditions, with E(t1) ∈ P and E(t2) ∈ O for a successful run over [t1, t2] — [paper PDF](https://www.cs.ubc.ca/~van/papers/2001-siggraph-composable.pdf)
- Arbitration: when no controller is active the supervisor polls all controllers; each bids an integer — 0 = unsuited, 1–10 = can take a sensible action from the current state, 10–20 = can handle the state *and* guarantee a transition to the desired goal state; the highest bid becomes active — [paper PDF](https://www.cs.ubc.ca/~van/papers/2001-siggraph-composable.pdf)
- Exactly three reasons a controller is deactivated (and so three transition kinds): (1) it declares success on reaching its post-condition; (2) user or higher-level planner intervention forces a transition; (3) it detects failure (e.g. a push or trip). Because of this the transition graph is "dynamic in structure" rather than a fixed FSM — [paper PDF](https://www.cs.ubc.ca/~van/papers/2001-siggraph-composable.pdf)
- Typical condition vocabulary: a balance predicate over support polygon S, gravity g, centre of mass c and its velocity (the figure is unbalanced if the gravity projection of c leaves S), plus target states/regions supplied by the user; pre-conditions may be taken from biomechanics literature (Pai & Patton's sagittal balance limits), derived by chaining (post-conditions of A dictate pre-conditions of B), found by manual experimentation, or *learned* by sampling the controller and training an SVM success/failure classifier — [paper PDF](https://www.cs.ubc.ca/~van/papers/2001-siggraph-composable.pdf); [C&G 2001 companion](https://web.cs.ucla.edu/~dt/papers/cag01/cag01.pdf)

**Task-level control over FSM controllers [H]**
- Coros, Beaudoin & van de Panne, "Robust Task-based Control Policies for Physics-based Characters" (SIGGRAPH Asia 2009, TOG 28, art. 170): precomputes task-level policies with reinforcement learning that choose among existing low-level controllers; tested on six locomotion tasks over three bipeds; the resulting policies are reported to be more robust than the controllers they are built from (search-level) — [project page](https://www.cs.ubc.ca/~van/papers/2009-TOG-taskControl/index.html)
- Coros, Beaudoin & van de Panne, "Generalized Biped Walking Control" (SIGGRAPH 2010, TOG 29, art. 130): a walking controller needing no character-specific tuning, combining PD tracking, inverted-pendulum foot placement and Jacobian-transpose virtual forces for gravity compensation and velocity tuning; extended to carrying crates, stepping over obstacles and climbing steps — a clear instance of separating intent (where the foot should land, what velocity to hold) from actuation (search-level) — [project page](https://www.cs.ubc.ca/~van/papers/2010-TOG-gbwc)

**Control graphs [H→E] (verified from the paper text)**
- Liu, van de Panne & Yin, "Guided Learning of Control Graphs for Physics-Based Characters", ACM TOG 35(3), art. 29, 2016 (DOI 10.1145/2893476): a control graph is built from *control fragments*, "each typically 0.1s in length"; each fragment is a short target tracking trajectory, its duration, and a linear feedback policy; feedback is applied once at the start of each fragment, so decisions are made at the ~0.1 s fragment time scale — [paper PDF](https://www.cs.ubc.ca/~van/papers/2016-TOG-controlGraphs/2016-TOG-controlGraphs.pdf); [project page](https://www.cs.ubc.ca/~van/papers/2016-TOG-controlGraphs/index.html)
- Transitions are *time-based at fragment boundaries* (not event-based): chains of fragments between transition states are "controllers"; "During online simulation, a motion planner or user input specifies a desired path through the control graph" — [paper PDF](https://www.cs.ubc.ca/~van/papers/2016-TOG-controlGraphs/2016-TOG-controlGraphs.pdf)
- Failure handling is by (a) robustness trained through long random walks on the graph in which every fragment appears at least 200 times, and (b) explicit recovery skills: "Four different standup strategies, each based on motion capture data, allow characters to recover from falls voluntarily." Robustness is quantified as the maximal recoverable horizontal trunk push of 0.1 s duration, increased in 10 N steps until the character falls within 20 cycles — [paper PDF](https://www.cs.ubc.ca/~van/papers/2016-TOG-controlGraphs/2016-TOG-controlGraphs.pdf)
- Control graphs persisted into the deep-RL era as an *authoring* device: Xie, Starke, Ling & van de Panne, "Learning Soccer Juggling Skills with Layer-wise Mixture-of-Experts" (SIGGRAPH 2022) lists "a control graph for authoring skills and transitions" among its contributions [E] — [project page](https://www.cs.ubc.ca/~van/papers/2022-SIGGRAPH-juggle/index.html)
- [C] The 2026 loco-manipulation paper LUCID characterises the prevailing practice it wants to replace as "scripted planners, finite-state machines, or task-specific model-free policies" sequencing whole-body skills — evidence that scripted FSM sequencing over learned skills is still the default glue in 2026 — [arXiv 2608.07746](https://arxiv.org/abs/2608.07746)
- [E] SIMS (2024) uses an LLM pipeline to produce interaction scripts whose execution is "managed by a finite state machine" of physics-based policies — [arXiv 2411.19921](https://arxiv.org/html/2411.19921v1)

**Behaviour trees and hierarchical state machines [E]**
- Colledanchise & Ögren, "Behavior Trees in Robotics and AI: An Introduction" (arXiv 1709.00084): BTs were developed in the game industry to increase modularity of NPC control; the claimed advantage over FSMs is modularity (FSM transitions are encoded inside states, like `goto`; BTs behave like function calls) and *reactivity* (conditions are re-evaluated on every tick so the tree can go back to previously completed sub-tasks); core control-flow nodes are Sequence, Fallback and Parallel, and every node returns Success, Failure or Running (search-level for wording) — [arXiv 1709.00084](https://arxiv.org/pdf/1709.00084); [IROS 2014 paper](https://people.kth.se/~petter/Publications/IROS14_co.pdf)
- Unreal Engine StateTree: "a general-purpose hierarchical state machine that combines the Selectors from behavior trees with States and Transitions from state machines"; a state completes as Stopped, Succeeded or Failed; transition triggers are OnStateCompleted, OnStateSucceeded, OnStateFailed, OnTick and OnEvent — i.e. success and failure are first-class, separately routable outcomes — [Epic StateTree overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-state-tree-in-unreal-engine); [EStateTreeTransitionTrigger API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/StateTreeModule/EStateTreeTransitionTrigger?lang=en-US)

### Inferences
- The generator "story" is a *sequential* phase machine in which the program counter is the state; this is semantically the SIMBICON/Hodgins pattern (state = active intents; transition = contact event or timeout) with nicer syntax. The library is therefore in a well-trodden lineage, not an outlier.
- What the lineage says is missing from a bare generator: (1) a failure channel — Faloutsos' "expected performance" predicate evaluated *every step*, not only at yield points, with a typed outcome (succeeded / failed / interrupted) as in StateTree; (2) declared pre-/post-conditions so stories can be chained and checked (post of "plant" ⊆ pre of "strike"); (3) timeouts on every wait (SIMBICON pairs event exits with elapsed-time exits; note also SIMBICON's rule of skipping a state whose exit event has already happened — a real edge case for `yield untilContact(...)`); (4) a recovery fallback (control graphs ship stand-up skills; BT Fallback nodes).
- SIMBICON's observation that target poses are deliberately unreachable supports naming the library's primitives "intents" rather than poses — the precedent is that an FSM state specifies *what to drive toward*, and the physical event ends it.

### Gaps
- I did not read Hodgins 1995 or SIMBICON full text in this session; state names and the precise transition rules come from search summaries and a secondary lecture deck.
- No primary source was found that documents *timeouts* as a named concept in these character-animation papers beyond SIMBICON's elapsed-time transitions; explicit timeout/abort semantics are documented in BT/StateTree tooling rather than in the animation literature.
- I did not verify Coros 2009/2010 details beyond project-page summaries.

## 2. Animation scripting languages and declarative motion specs (Improv, BML, Laban-based systems, spacetime constraints, keyframe-plus-physics tools, coroutine/generator scripting)

### Takeaway
Declarative specs converge on two ideas the library can borrow directly: **named synchronisation points inside a behaviour (BML's start/ready/stroke/relax/end) with a feedback channel that reports progress, warnings and failures**, and the **"what" (constraints) vs "how" (objective) split** of spacetime constraints. Generator/coroutine scripting is the mainstream idiom for sequential animation logic in games and creative coding (Motion Canvas, Unity, Lua), with `all / any / chain / sequence` combinators as the established vocabulary for concurrency.

### Cited Findings

**Scripting languages for actors [H]**
- Improv (Perlin & Goldberg, SIGGRAPH 1996): a two-part system — an Animation Engine that layers and blends procedural actions, and a Behavior Engine in which authors write rules/scripts in an "English-style" scripting language so that non-programmers can author interactive actors; actions are grouped by compatibility, actions in different groups run concurrently (walk while scratching head) while actions within a group compete with graceful transitions (search-level) — [paper page](https://mrl.cs.nyu.edu/~perlin/improv-paper); [PDF](https://mrl.cs.nyu.edu/publications/sig96-improv/sig96-improv.pdf)
- BML (Behavior Markup Language, SAIBA framework; Vilhjálmsson et al., IVA 2007; BML 1.0 standard): BML is the middle layer between intent planning and behaviour realisation. Each behaviour is divided into phases bounded by seven standard *sync points* — start, ready, stroke-start, stroke, stroke-end, relax, end — and behaviours are aligned by constraining one behaviour's sync point to another's (e.g. gesture stroke to a word) — [BML 1.0 standard wiki](https://projects.cs.ru.is/projects/behavior-markup-language/wiki); [BML 1.0 PDF](https://projects.cs.ru.is/attachments/download/843/bml-standard-1.pdf); [Kopp et al. overview](https://core.ac.uk/download/211846553.pdf)
- BML feedback: the realizer sends the planner *prediction* feedback (expected timing), *progress* feedback (block start/end and sync points reached) and *warning* feedback (part of a block failed); the standard describes feedback as the means by which planners monitor progress and recover from errors; implementations distinguish a warning (something did not work as expected) from an exception (the BML block failed completely) — [BML 1.0 standard wiki](https://projects.cs.ru.is/projects/behavior-markup-language/wiki); [bml_realizer docs](https://rosbmlrealizer.sourceforge.net/bml_realizer/html/index.html)
- EMOTE (Chi, Costa, Zhao & Badler, SIGGRAPH 2000, pp. 173–182): uses Laban Movement Analysis *Effort* and *Shape* as a small set of qualitative parameters applied on top of independently defined movements (key poses + timing) to procedurally synthesise expressive arm/torso gestures — a "manner" layer orthogonal to "what" — [paper PDF](https://www.cis.upenn.edu/~badler/siggraph00/emote.pdf); [SIGGRAPH archive](https://history.siggraph.org/?p=118266)

**Constraint/optimisation as specification [H]**
- Witkin & Kass, "Spacetime Constraints", SIGGRAPH 1988: the animator specifies "what the character has to do, for instance, 'jump from here to there, clearing a hurdle in between'" and "how the motion should be performed, for instance 'don't waste energy'"; these together with Newton's laws form a constrained optimisation whose solution is the motion (demonstrated on Luxo). "What" = constraints; "how" = objective; physics = constraint — [SIGGRAPH archive](https://history.siggraph.org/?p=119573); [paper copy](https://www.cs.hmc.edu/courses/2006/spring/cs157/papers/spacetime.pdf); [Wisconsin lecture notes](https://pages.graphics.cs.wisc.edu/777-13/2013/05/07/lecture-27-spacetime-constraints/)

**Keyframe-plus-physics authoring tools [E/C]**
- Cascadeur AutoPhysics: a set of tools that analyses the authored (keyframed) animation and proposes a physically plausible version; the Physics Corrector is the core; the author controls *how much the solver may deviate* through Key Frame Weight (preserve translation/rotation on keyframes) and Frame Weight (on interpolated frames) and through priority frames — and the docs warn that too many priority frames can leave the algorithm unable to find a fitting solution (i.e. over-constraint is surfaced as a documented failure mode, not a diagnostic) — [AutoPhysics docs](https://cascadeur.com/help/tools/physics_tools/autophysics); [AutoPhysics settings](https://cascadeur.com/help/tools/physics_tools/autophysics/autophysics_settings)
- Cascadeur *Fulcrum Points*: contacts are declared per keyframe interval — a point is treated as a fulcrum when it "doesn't move beyond the max speed multiplied by the number of frames between the keyframes", and a fulcrum state applies to the current keyframe and the interpolation interval after it; the physics tools depend on these contact declarations — [Fulcrum Points docs](https://cascadeur.com/help/tools/physics_tools/fulcrum_points)
- NaturalMotion Endorphin (offline, discontinued 2014) and Euphoria (runtime, first shipped in GTA IV) used "Dynamic Motion Synthesis": authors pick and parameterise *adaptive behaviours* (e.g. tackle when a rival is close; break a fall with the arms) on a simulated character and see the result immediately rather than keyframing [H] — [Wikipedia: NaturalMotion](https://en.wikipedia.org/wiki/NaturalMotion); [Wikipedia: Endorphin](https://wikipedia.com/wiki/Endorphin_(software))

**Coroutine / generator scripting [E/C]**
- Motion Canvas (TypeScript): "Motion Canvas uses generator functions to describe animations"; `yield` means "The current frame is ready, display it on the screen and come back to me later"; `yield*` "allows us to delegate the yielding to another generator"; tweens are generators; *flow generators* "take one or more generators as their input and combine them together": `all` ("Run all tasks concurrently and wait for all of them to finish"), `any` ("...wait for any of them to finish"), `chain` (one after another), `delay`, `sequence` (start with a constant stagger), `loop` — [Motion Canvas flow docs](https://motioncanvas.io/docs/flow); [quickstart](https://motioncanvas.io/docs/quickstart)
- Unity: `WaitUntil` is a yield instruction that "suspends the coroutine execution until the supplied delegate evaluates to true"; the delegate is polled every frame after `Update` and before `LateUpdate` — the canonical "yield a predicate" precedent for the library's wait-conditions — [Unity ScriptReference: WaitUntil](https://docs.unity3d.com/2018.1/Documentation/ScriptReference/WaitUntil.html)
- Lua coroutines are the long-standing idiom for cutscenes and action sequences in games precisely because they replace hand-managed booleans/state flags with straight-line code plus `wait(...)` helpers that yield in a loop until a time or condition is met — [edw.is: action sequences and cutscenes](https://edw.is/how-to-implement-action-sequences-and-cutscenes/); [Leadwerks coroutine sequences](https://www.leadwerks.com/community/blogs/entry/2432-coroutine-sequences/)
- GSAP timelines are the *declarative-timeline* alternative: tweens are placed with a position parameter (absolute seconds, relative offsets such as `"+=0"`/`"<"`, labels, and percentage-based values since 3.7.0) rather than by control flow — good for fixed-duration choreography, with no native notion of waiting on a physical event — [GSAP position parameter](https://gsap.com/resources/position-parameter/); [GSAP Timeline docs](https://gsap.com/docs/v3/GSAP/Timeline)
- Theatre.js: a sequence is an authored timeline with playback controls (rate, iteration count, range, play/pause/position) — again time-indexed rather than event-indexed (seen only via the Threlte wrapper docs) — [Threlte Theatre sequence reference](https://threlte-git-studio-threlte.vercel.app/docs/reference/theatre/sequence)

### Inferences
- The library's `yield waitCondition` is the Unity `WaitUntil` / Lua `wait_until` idiom applied to *physical* events; Motion Canvas supplies the best-established TypeScript vocabulary for composing generators (`all`, `any`, `chain`, `sequence`, `delay`, `loop`, and `yield*` for sub-stories). Adopting those names verbatim would lower the learning curve for humans and LLMs. `any(waitForContact, timeout(0.4))` is the natural way to express SIMBICON's event-or-elapsed-time exits.
- BML suggests two cheap, high-value additions: (a) named sync points on each intent (e.g. a "drive" has `start → ready (wind-up complete) → stroke (impact) → relax → end`), so other intents can be aligned to them declaratively instead of by ad-hoc predicates; (b) a typed feedback stream (prediction / progress / warning / exception) from the runtime to the author or LLM.
- Spacetime constraints' what/how split maps onto the library as: named placements and outcome targets = constraints ("what"); settle/effort/style parameters = objective ("how"). Keeping these syntactically separate is the oldest design lesson in the field.
- Timelines (GSAP, Theatre.js) and generators are complementary: timelines suit fixed-duration choreography; generators suit event-contingent control flow, which is what physically simulated motion needs because durations are outcomes, not inputs.

### Gaps
- Rive scripting (Luau, 2025) was in scope but I found no primary documentation in this session; not covered.
- The Motion Canvas threading/cancellation page could not be retrieved (the fetch resolved to an unrelated site), so `spawn`/`cancel`/`join` semantics and `waitFor`/`waitUntil` are not documented here from a primary source.
- Labanotation *as a notation driving animation* (as opposed to LMA Effort/Shape in EMOTE) was not found; no reliable source located.
- Endorphin/Euphoria behaviour parameter lists are not publicly documented in anything I found; the description rests on Wikipedia and press material.
- Theatre.js was seen only through a third-party wrapper's docs.

## 3. LLM- and language-driven motion (text-to-motion as authoring, LLM-written rewards/controllers, LLM planners over skill libraries, LLM-written animation code, 2025–2026 agentic authoring)

### Takeaway
Three interface patterns dominate: (1) **LLM writes a reward/cost in code and an optimiser (RL or MPC) realises it** (Language-to-Rewards, Eureka, Text2Reward; still an active line in 2026 with agentic "reward design agents"); (2) **LLM emits a structured intermediate plan — contact sequences, keyframes, skill calls — executed by a unified low-level controller** (UniHSI's Chain-of-Contacts, SIMS, typed skill libraries); (3) **end-to-end text-conditioned physics controllers** (MaskedMimic 2024 → ADAPT, LYRIC in 2026). I found no 2025–2026 primary source in which an LLM writes *procedural character-controller code* of the kind the library targets; the closest are Code-as-Policies-style robot programs and LLM-written 2D animation code (LogoMotion, Keyframer).

### Cited Findings

**LLM → reward code → optimiser [E→C]**
- Language to Rewards (Yu et al., CoRL 2023, PMLR 229:374–404; arXiv 2306.08647): rewards are the interface between language and low-level control; a *Reward Translator* consists of a Motion Descriptor that expands the user instruction into a templated natural-language description of the desired motion, and a coder LLM that turns it into reward code; MuJoCo MPC then optimises actions in real time, which makes interactive correction possible; evaluated on 17 tasks on a simulated quadruped and a dexterous manipulator, with reported 90% task success, and on a real arm — [arXiv 2306.08647](https://arxiv.org/abs/2306.08647); [PMLR](https://proceedings.mlr.press/v229/yu23a.html); [Google Research blog](https://www.research.google/blog/language-to-rewards-for-robotic-skill-synthesis/)
- Eureka (Ma et al., ICLR 2024): GPT-4 writes reward code zero-shot from raw environment source plus a task description, then improves it by evolutionary search with "reward reflection" on training statistics; reported to outperform human-engineered rewards — [project page](https://eureka-research.github.io)
- Text2Reward (Xie et al., ICLR 2024; arXiv 2309.11489): generates dense reward code grounded in a compact environment representation and "incorporates human feedback to iteratively refine the generated reward codes", addressing language ambiguity — [arXiv 2309.11489](https://arxiv.org/pdf/2309.11489)
- [C] RDA: Reward Design Agent (arXiv 2606.01672, June 2026) criticises Eureka: it "frequently produces misaligned rewards because its reflection loop lacks visual assessment and relies solely on coarse reward statistics"; on HumanoidBench it reports Eureka policies that "violate task specifications (e.g., throwing packages rather than pushing them)" — a concrete instance of an outcome objective being satisfied by the wrong motion (claim by the RDA authors, not independently verified) — [arXiv 2606.01672](https://arxiv.org/html/2606.01672v1)

**LLM → code/plan over skills [E→C]**
- Code as Policies (Liang et al., 2022; arXiv 2209.07753): code-writing LLMs produce robot policy code from natural language that can express both reactive policies (e.g. impedance controllers) and waypoint-based policies by recomposing API calls, with hierarchical code generation that recursively defines undefined functions; stated limits: it is bounded by what the perception APIs can describe and which control primitives exist, and struggles with instructions much more complex than its few-shot examples — [arXiv 2209.07753](https://arxiv.org/abs/2209.07753); [project page](https://code-as-policies.github.io)
- SayCan is characterised (by the Code-as-Policies authors) as producing feasible plans by jointly decoding an LLM weighted by skill *value functions* — affordance grounding over a fixed skill set — [arXiv 2209.07753](https://arxiv.org/pdf/2209.07753)
- UniHSI (Xiao et al., ICLR 2024; arXiv 2309.07918): "a high-level LLM Planner to translate language inputs into the task plans in the form of CoC [Chain of Contacts] and a low-level Unified Controller for executing these plans"; a Chain of Contacts is a sequence of steps each defined by human-joint ↔ object-part contact pairs; the controller is trained without annotated motion sequences — [arXiv 2309.07918](https://arxiv.org/html/2309.07918v5); [ICLR proceedings](https://proceedings.iclr.cc/paper_files/paper/2024/hash/6a6ecedac816a24f92ad1f444b1edcb0-Abstract-Conference.html)
- AnySkill (Cui et al., CVPR 2024; arXiv 2403.12835): a low-level controller learns a repertoire of atomic actions by imitation; a high-level policy composes them for an open-vocabulary instruction by maximising CLIP similarity between rendered images of the agent and the text — no hand-written reward — [CVPR open access](https://openaccess.thecvf.com/content/CVPR2024/html/Cui_AnySkill_Learning_Open-Vocabulary_Physical_Skill_for_Interactive_Agents_CVPR_2024_paper.html)
- InsActor (Ren et al., NeurIPS 2023; arXiv 2312.17135): a diffusion model plans state sequences from instructions and these are mapped to latent skill vectors executed by a physics-based character controller — [arXiv 2312.17135](https://arxiv.org/pdf/2312.17135)
- SIMS (2024; arXiv 2411.19921): LLM-generated interaction "scripts" executed through an FSM of physics-based policies for long-horizon human–scene interaction — [arXiv 2411.19921](https://arxiv.org/html/2411.19921v1)
- A 2024 two-agent system has one multimodal LLM design keyframes and another animate a humanoid through a tracking policy — [arXiv 2406.10740](https://arxiv.org/html/2406.10740v1)
- [C] Re²MoGen (arXiv 2604.17807, April 2026): Monte-Carlo tree search enhances an LLM's reasoning when generating motion *keyframes* from text, followed by physics-aware RL refinement — LLM as sparse-keyframe planner, physics as post-process — [arXiv 2604.17807](https://arxiv.org/abs/2604.17807)
- [C] "Physical Agentic AI" (arXiv 2608.22657, Aug 2026): a foundation-model planner restricted to each robot's *typed skill library*, decomposing tasks into phases and validating each skill call before execution — [arXiv 2608.22657](https://arxiv.org/html/2608.22657v1)
- [C] An LLM-cascade system for a quadruped decomposes a language task into a plan of *parameterised skill calls* (arXiv 2404.05291) — [arXiv 2404.05291](https://arxiv.org/html/2404.05291/)

**Text-conditioned physics controllers [E→C]**
- MaskedMimic (Tessler, Guo, Nabati, Chechik & Peng, ACM TOG / SIGGRAPH Asia 2024; DOI 10.1145/3687951): see §4; text is one of several maskable conditioning modalities — [NVIDIA project page](https://research.nvidia.com/labs/par/maskedmimic/); [arXiv 2409.14393](https://arxiv.org/html/2409.14393v1)
- [C] ADAPT (Wu, Li, Zhao, Li, Hutter & Tang; arXiv 2609.00677, 1 Sep 2026): end-to-end closed-loop text-driven humanoid control — a diffusion action prior learned from text-labelled state–action trajectories, with a lightweight residual RL policy on the frozen diffusion controller for long-horizon robustness and smooth prompt switching; no kinematic generate-then-track stage; abstract gives no quantitative metrics — [arXiv 2609.00677](https://arxiv.org/abs/2609.00677)
- [C] LYRIC (Han et al.; arXiv 2609.19688, 17 Sep 2026): flow-matching controller for language-driven, contact-rich whole-body object interaction, conditioned on a free-form instruction plus *a sparse goal for the object's final position*; split into a task-level planner (short-horizon object and root trajectories) and a closed-loop action generator; reports 90.3% task success on a held-out split vs 74.2% for the strongest kinematic-planner baseline, and supports test-time object-waypoint guidance without retraining — [arXiv 2609.19688](https://arxiv.org/abs/2609.19688)
- [C] "Commanding Humanoid by Free-form Language: A Large Language Action Model with Unified Motion Vocabulary" (arXiv 2511.22963, Nov 2025) — title-level evidence of the LLM-with-motion-tokens approach reaching humanoid control — [arXiv 2511.22963](https://arxiv.org/pdf/2511.22963)

**Conversational motion generation/editing (kinematic) [E→C]**
- MotionFix (2024; arXiv 2408.00712): first text-based motion *editing* dataset (source motion, edit text, target motion) and TMED, a diffusion model conditioned on source motion and edit text — [arXiv 2408.00712](https://arxiv.org/html/2408.00712v3)
- Motion-Agent (arXiv 2405.17013): a conversational framework for motion generation, editing and understanding; its MotionLLM adds motion tokens to a pre-trained LLM's vocabulary and fine-tunes with lightweight adapters — [arXiv 2405.17013](https://arxiv.org/html/2405.17013v3)
- [C] PartMotionEdit (arXiv 2512.24200, Dec 2025): fine-grained, body-part-level text-driven editing, motivated by global methods struggling with part-specific edits — [arXiv 2512.24200](https://arxiv.org/html/2512.24200)

**LLM-written animation code [E]**
- LogoMotion (CHI 2024; arXiv 2405.07065): "Visually-Grounded Code Synthesis for Creating and Editing Animation" — an LLM writes animation code for 2D layouts with a visual check-and-repair loop (title/abstract level) — [arXiv 2405.07065](https://arxiv.org/pdf/2405.07065)
- "Real-time Animation Generation and Control on Rigged Models via Large Language Models" (arXiv 2310.17838, 2023) is cited in surveys as LLM-driven animation of rigged characters; a 2025 survey of generative AI for character animation covers LLMs as one foundation-model family but does not treat LLM-written controller code specifically — [arXiv 2504.19056](https://arxiv.org/html/2504.19056v1)

### Inferences
- A generator story of named intents and wait-conditions is, in LLM-interface terms, a "Code as Policies" program over a typed skill/intent API — pattern (2). The literature's recurring lesson for that pattern is that the LLM is bounded by the vocabulary of primitives and by what state it can observe; hence the value of a *small, typed, well-documented* intent API and of feeding execution feedback back to the model (Text2Reward's human-feedback loop, RDA's criticism that statistic-only reflection misaligns).
- UniHSI's Chain-of-Contacts is the closest published analogue to "plant the left foot beside the ball, strike with the right instep": a contact-pair sequence as the LLM-facing intermediate representation. Named contact pairs (body part ↔ world/object anchor) are a better-established abstraction than free-form foot coordinates.
- The Eureka failure reported by RDA (throwing instead of pushing) is the generic risk of outcome-only specification: an outcome-targeted "drive" needs accompanying manner constraints (which limb, which contact, which phase), or the optimiser will meet the number by the wrong motion.
- The 2026 frontier (ADAPT, LYRIC) is moving *away* from interpretable scripts toward closed-loop generative controllers with sparse goals; scripts remain the practical glue (LUCID's remark, §1) and are the only approach that needs no training data — the library's niche.

### Gaps
- No 2025–2026 primary source was found on LLMs or agents authoring *procedural/physics character-controller code* (as opposed to rewards, keyframes, or robot pick-and-place programs). This appears to be a real gap in the literature, but absence from my searches is weak evidence.
- Not verified in this session (I believe these exist but did not retrieve them, so treat as leads): MotionGPT (Jiang et al., NeurIPS 2023), CLoSD (Tevet et al., ICLR 2025, diffusion planner + tracking controller in closed loop), SayCan's primary paper (arXiv 2204.01691), Eureka's and Text2Reward's headline numbers.
- No reliable source found on Blender/DCC agentic animation tooling (MCP-style) in 2025–2026.
- ADAPT, LYRIC, RDA, Re²MoGen and LUCID are 2026 arXiv preprints with no confirmed venue; results are author-reported.

## 4. Outcome and constraint specification (task goals, masked constraints, trajectory-optimisation objectives, temporal logic; reporting infeasible goals)

### Takeaway
Outcome targets are specified in three established ways: as **goal inputs + task reward** to a learned policy (DeepMimic strike/throw), as **sparse spatio-temporal constraints that a controller "inpaints"** (MaskedMimic), or as **constraints/objectives of an optimisation** (spacetime constraints, MPC, STL). Only the formal-methods route has a principled answer to infeasibility — a signed *robustness degree* and *minimal-relaxation* reporting ("how much must the goal be loosened"); learned controllers generally fail silently or approximately.

### Cited Findings
- DeepMimic (Peng et al., SIGGRAPH 2018; arXiv 1804.02717): total reward is a weighted sum of an imitation reward and a task reward. *Strike*: hit a randomly placed spherical target with a specified link (e.g. a foot); success when the link's centre is within 0.2 m of the target; the goal input is the target location. *Throw*: same goal/reward structure but a ball must hit the target, with ball position, rotation and velocities added to the state. The authors report that dropping either term degrades results (search-level) — [arXiv 1804.02717](https://arxiv.org/pdf/1804.02717); [project page](https://xbpeng.github.io/projects/DeepMimic)
- MaskedMimic (2024): "formulates physics-based character control as a general motion inpainting problem"; trained on randomly masked motion sequences, the policy predicts actions that reproduce the full motion; at use time the author supplies any subset of constraints — sparse joint targets/keyframes at chosen times, text, objects, paths — and combinations thereof, with one unified controller — [NVIDIA project page](https://research.nvidia.com/labs/par/maskedmimic/); [arXiv 2409.14393](https://arxiv.org/html/2409.14393v1)
- [C] MaskedManipulator (arXiv 2505.19086, 2025) extends the masked-goal idea to whole-body manipulation with sparse object/body goals; [C] LYRIC (2026) conditions on language plus a sparse final object position and accepts test-time object waypoints — [arXiv 2505.19086](https://arxiv.org/html/2505.19086); [arXiv 2609.19688](https://arxiv.org/abs/2609.19688)
- Sports outcome targets in simulation [E/C]: SMPLOlympics (Luo et al., arXiv 2407.00187, 2024) provides physically simulated humanoid environments for 10 sports including javelin throw, golf, high/long jump, hurdling, and soccer incl. a penalty-kick environment; finding: strong motion priors plus simple task rewards produce human-like behaviour (e.g. agents discover the Fosbury flop) — [arXiv 2407.00187](https://arxiv.org/html/2407.00187); [project site](https://smplolympics.github.io/SMPLOlympics-Site)
- PhysicsFC (Kim, Jung & Lee, SIGGRAPH 2025; arXiv 2504.21216): user-controlled physically simulated football player with dribble, trap, move and kick skills and a simulated ball; kick skill policies output latents for a pretrained motion-embedding model and must send the ball in the desired direction with the intended force [C] — [arXiv 2504.21216](https://arxiv.org/html/2504.21216v2)
- Hong, Han, Cho, Shin & Noh, "Physics-based full-body soccer motion control for dribbling and shooting" (SIGGRAPH 2019) is the earlier dedicated shooting controller [E] — [SIGGRAPH archive](https://history.siggraph.org/?p=100135)
- Spacetime constraints (1988): outcome requirements are hard constraints ("jump from here to there, clearing a hurdle"), manner is the objective (minimise power); infeasibility shows up as optimiser non-convergence, with no diagnostic in the original formulation [H] — [SIGGRAPH archive](https://history.siggraph.org/?p=119573)
- Signal Temporal Logic for legged robots [E]: Gu et al., "Robust-Locomotion-by-Logic" (arXiv 2403.15993; earlier "Walking-by-Logic", arXiv 2310.11290) write push-recovery and foot-placement tasks for the biped Cassie as STL specifications inside an MPC; STL "admits quantitative semantics to assess specification satisfaction, which is referred to as robustness degree", and that robustness is used as the objective; includes stepping-stone selection from disjoint footholds; validated in simulation and hardware — [arXiv 2403.15993](https://arxiv.org/abs/2403.15993)
- Infeasible STL specs — minimal relaxation: Buyukkocak & Aksaray (CDC 2022; arXiv 2208.08384) relax the *time bounds* of STL sub-tasks via a mixed-integer program with a normalised relaxation metric (0 = no relaxation needed, 1 = sub-task dropped); [C] Wu & Lyu (arXiv 2603.06947, March 2026) restore MPC feasibility by an L1-minimal relaxation of *state* constraints followed by Pareto refinement, explicitly to avoid the "freezing" fallback of conservative controllers — [arXiv 2208.08384](https://arxiv.org/abs/2208.08384v2); [arXiv 2603.06947](https://arxiv.org/html/2603.06947v1)
- Tool-level infeasibility: Cascadeur documents that too many priority frames may leave the physics corrector unable to find a solution; BML realizers report unsatisfiable or unsupported behaviours through warnings/exceptions (see §2) — [Cascadeur AutoPhysics settings](https://cascadeur.com/help/tools/physics_tools/autophysics/autophysics_settings); [BML 1.0 standard](https://projects.cs.ru.is/projects/behavior-markup-language/wiki)

### Inferences
- An outcome-targeted "drive" ("ball leaves at 27 m/s") corresponds to DeepMimic's task goal or a spacetime terminal constraint; the well-established complement is a *tolerance* (DeepMimic's 0.2 m radius) — outcomes should be stated as target + tolerance, which also defines success for the story's post-condition.
- STL robustness gives the cleanest model for reporting infeasibility: return a signed margin per constraint (e.g. "achieved 23.1 m/s of 27 ± 1; torque-limited at hip for 85 ms") and, following the relaxation literature, the *smallest relaxation that would have succeeded* (time window, target magnitude). This is more useful to an LLM author than a boolean failure.
- STL's bounded temporal operators (eventually-within-[a,b], always-during) are a formal counterpart of "yield until event, with timeout"; a story could be *checked* against an STL-like trace monitor without being authored in STL.
- MaskedMimic's lesson for API design: let any subset of constraints be omitted; the system fills in the rest. In a procedural system the analogue is defaults for every unspecified intent (posture, arms, gaze), so sparse scripts stay valid.

### Gaps
- I found no source describing how learned controllers (DeepMimic-style, MaskedMimic, PhysicsFC) *report* an unreachable goal; the papers evaluate success rates but, as far as I could find, expose no per-request feasibility signal.
- "Unsat-core"/diagnosis work for STL (explaining *why* a spec is infeasible) was not found in this session.
- PhysicsFC's and SMPLOlympics' exact kick-velocity reward terms were not retrieved.
- Trajectory-optimisation tooling for characters after spacetime constraints (e.g. contact-invariant optimisation, MuJoCo MPC cost authoring) was not researched beyond its use in Language-to-Rewards.

## 5. Sports-biomechanics knowledge such scripts encode (kinetic chain, instep kick, javelin, plant/block leg) with reference values

### Takeaway
Both skills are proximal-to-distal whips built on a braked support leg: in the kick the thigh peaks (~516–573 deg/s) and decelerates as the shank accelerates to ~1900 deg/s at impact, with peak hip-flexion moments of ~190–310 N·m and knee-extension moments of ~70–160 N·m — but the knee extensor moment *falls to zero or reverses just before impact* and the final shank acceleration is driven by motion-dependent (interaction) moments. In the javelin, peak hip, shoulder and elbow speeds occur about 130, 90 and 60 ms before release, release speed is ~28–30 m/s for 84–90 m throws, and less block-knee flexion correlates with distance (r = −0.59).

### Cited Findings

**Instep kick — sequence and segment speeds** (Kellis & Katis 2007 review, J Sports Sci Med 6:154–165, read from the PDF; Lees et al. 2010 review, J Sports Sci 28(8):805–817, DOI 10.1080/02640414.2010.481305, read from a full-text copy)
- Proximal-to-distal: "angular velocity is maximized first by the thigh, then by the shank and finally by the foot". Early forward swing: thigh angular velocity ≈ +286–401 deg/s while the shank is ≈ −286–401 deg/s (still swinging back). Thigh peaks at ≈ 516–573 deg/s just before the knee begins to extend; the thigh then decelerates while shank velocity rises roughly linearly to ball impact, reaching 1891 deg/s (Dörge et al. 1999); at impact thigh angular velocity is almost zero — [Kellis & Katis 2007 PDF](https://www.jssm.org/volume06/iss2/cap/jssm-06-154.pdf)
- Backswing: hip extends up to 29° with hip angular velocity 171.9–286.5 deg/s; ankle plantarflexion velocity up to 860 deg/s; knee extension velocity during the swing 860–1720 deg/s — [Kellis & Katis 2007 PDF](https://www.jssm.org/volume06/iss2/cap/jssm-06-154.pdf)
- Peak knee-extension angular velocity in adult/trained males across studies: 1134 (±257) to 1874 (±155) deg/s (e.g. Lees & Nolan 2002: 1364 ± 80 high-speed kick vs 1175 ± 75 accurate kick; Levanon & Dapena 1998: 1805 ± 289; Nunome 2002: 1364 ± 298; Barfield 1995: 1587 ± 280); children 4.4 y: 1014 deg/s — [Kellis & Katis 2007 PDF, Table 4](https://www.jssm.org/volume06/iss2/cap/jssm-06-154.pdf)
- A later conference paper reports shank forward-swing angular velocity peaking at 2051 ± 205 deg/s at ball impact (search-level; originating study not confirmed) — [ISBS proceedings](https://ojs.ub.uni-konstanz.de/cpa/article/view/1172)

**Instep kick — joint moments (kicking leg)**
- Peak/average moments in adult males (Kellis & Katis Table 1; hip flexion / knee extension, N·m): Nunome 2002 average 249 (31) / 98 (27), maximal 283 (30) / 111 (39); Nunome 2006a maximal 309.2 (28.9) / 129.9 (25.5); Putnam 1991 average 229 (34) / 85 (12); Dörge 1999 maximal 271.3 / 161.0; Zernicke & Roberts 1978 maximal 274 (36) / 122 (23); Robertson 1985 220 / 90; Luhtanen 1988 194 (33) / 83 (21) with ankle plantarflexion 20 (4). Hip flexion moments are roughly twice knee extension moments; ankle plantarflexion 20–30 N·m; ankle inversion 15–20 N·m; hip adduction ≈ 115 N·m — [Kellis & Katis 2007 PDF](https://www.jssm.org/volume06/iss2/cap/jssm-06-154.pdf)
- Experienced vs inexperienced players (Kawamoto et al. 2007): hip flexion / adduction / external-rotation moments 168 / 100 / 41 N·m vs 94 / 115 / 26 N·m — [Lees et al. 2010 full text](https://numerik.mi.fu-berlin.de/wiki/WS_2020/CoMaI_Dokumente/FTVS-2332-version1-the_biomechanics_of_kicking_in_soccer_a_review.pdf)
- Moment timing: hip flexion moment peaks at roughly 25–30% of kick duration; knee moment peaks follow the hip peaks; both decline sharply just before impact, with an almost minimal hip moment at ball impact (Nunome 2006b) — [Kellis & Katis 2007 (HTML)](https://www.jssm.org/jssm-06-154.xml>Fulltext)
- Motion-dependent moments: with appropriate filtering, the shank is still accelerating until impact; "the knee extension moment rapidly decreased during the final phase of kicking and finally began to exhibit a reverse (flexion) moment immediately before ball impact, while the motion-dependent moment rapidly increased" (Nunome 2006a); the interpretation is that shank angular velocity exceeds the muscles' force–velocity limit so they can no longer generate concentric force. Dörge et al. (2002): work by the motion-dependent moment due to thigh angular velocity ≈ 20% of the work done by the knee-extension moment. The upward lift of the hip — produced by the *support leg* — contributes to this interaction moment late in the swing (Nunome & Ikegami 2005) — [Lees et al. 2010 full text](https://numerik.mi.fu-berlin.de/wiki/WS_2020/CoMaI_Dokumente/FTVS-2332-version1-the_biomechanics_of_kicking_in_soccer_a_review.pdf); [Nunome & Ikegami 2005, ISBS](https://ojs.ub.uni-konstanz.de/cpa/article/view/1172)

**Instep kick — ball speed, impact**
- Ball speed for maximal instep kicks: 18–35 m/s depending on skill, age, approach and limb; examples (mean ± SD, m/s): professionals 29.9 ± 2.9 (Asami & Nolte 1983); skilled 24.7 ± 2.5 (Dörge 2002); experienced 28.0 ± 2.1 (Nunome 2002); skilled 16.8-year-olds 32.1 ± 1.7 (Nunome 2006a); experienced 26.3 ± 3.4 (Nunome 2006b); intercollegiate 28.6 ± 2.2 (Levanon & Dapena 1998); 1990 World Cup 32–35 (Ekblom 1994). So 27 m/s sits in the range of experienced/skilled adult players — [Kellis & Katis 2007 PDF, Table 3](https://www.jssm.org/volume06/iss2/cap/jssm-06-154.pdf)
- Ball-to-foot speed ratio 1.06–1.65 depending on which point of the foot is used for foot speed; ball and foot speed correlate at r > 0.74; coefficient of restitution 0.463–0.681, and raising it from 0.5 to 0.65 would raise ball speed by about 10% (Bull-Andersen 1999) — [Kellis & Katis 2007 (HTML)](https://www.jssm.org/jssm-06-154.xml>Fulltext)
- "Foot–ball contact lasts for less than 10 ms" (Nunome 2006b); peak impact force can exceed 2800 N in a maximal kick; the foot remains in contact over a travel of about 2/3 of a ball diameter (Asai 2002) — [Lees et al. 2010 full text](https://numerik.mi.fu-berlin.de/wiki/WS_2020/CoMaI_Dokumente/FTVS-2332-version1-the_biomechanics_of_kicking_in_soccer_a_review.pdf); [Kellis & Katis 2007 (HTML)](https://www.jssm.org/jssm-06-154.xml>Fulltext)
- Off-centre impact trade-off (Carré 2002 simulation): a 26 m/s no-spin kick becomes 18.5 m/s with 64 rad/s spin when struck 8 cm off-centre at the same foot speed; maximum reported ball spin 101 rad/s — [Lees et al. 2010 full text](https://numerik.mi.fu-berlin.de/wiki/WS_2020/CoMaI_Dokumente/FTVS-2332-version1-the_biomechanics_of_kicking_in_soccer_a_review.pdf)

**Instep kick — approach, plant (support) leg, trunk** (all from Lees et al. 2010 unless noted) — [Lees et al. 2010 full text](https://numerik.mi.fu-berlin.de/wiki/WS_2020/CoMaI_Dokumente/FTVS-2332-version1-the_biomechanics_of_kicking_in_soccer_a_review.pdf)
- Approach: angled, curved, 2–4 steps, approach angle around 45° gave maximum ball speed (Isokawa & Lees 1988); approach speed is modest, around 3–4 m/s; last step is longer in maximal kicks (0.72 and 0.81 m vs 0.53 and 0.55 m sub-maximal, two professionals; Lees & Nolan 2002), associated with greater pelvic retraction.
- Support-foot ground reaction forces for a maximal instep kick: 15–20 N/kg vertical, 4–6 N/kg posterior (braking), 5–6 N/kg lateral (Kellis, Katis & Gissis 2004).
- Support knee: flexed 26° at foot contact and stays flexed, 42° at ball contact (Lees et al. 2009); the slow knee motion lets its muscles generate their highest forces and stabilises the action. Support-leg flexion/extension joint moments: 4.0, 3.2 and 2.2 N·m/kg at hip, knee and ankle (Lees et al. 2009). Support-leg shank lateral inclination ≈ 25° (text truncated in my copy at this value).
- Support-foot placement: 5–10 cm behind and 5–28 cm beside the ball has been suggested (Hay 1993) but not confirmed experimentally; Lees et al. note no recent data on this — [Kellis & Katis 2007 (HTML)](https://www.jssm.org/jssm-06-154.xml>Fulltext)
- Trunk at ball contact: backward lean 13° (low-trajectory) and 17° (high-trajectory) in skilled players (Prassas 1990); 12° and 0° backward with 10° and 16° lateral lean to the non-kicking side for two professionals (Lees & Nolan 2002).
- Pelvis: retraction-to-protraction range 30–36° in skilled players; rapid change in pelvic tilt and rotation ≈ 50 ms before ball contact; the pelvis is raised on the kicking side at contact (10–15°), allowing greater knee extension and foot speed.
- Hip–shoulder separation range 38° and 42° in maximal kicks vs 6° and 12° sub-maximal (Lees & Nolan 2002). The "tension arc" (Shan & Westerhoff 2005) runs from the withdrawn kicking leg to the extended, abducted non-kicking-side arm and is released ("shorten arc") in the forward swing — a stretch–shorten mechanism, with the arm contributing to velocity rather than only balance.
- Lees (2007) names five principles applicable to kicking: range of motion, stretch–shorten cycle, end-point speed, action–reaction, proximal-to-distal sequence.

**Javelin**
- Release speed and geometry, men's final, 1999 World Championships (Campos, Brizuela & Ramón, New Studies in Athletics 19, pp. 47–57; 3D video at 50 Hz, 7 finalists): release velocity 28.1–29.7 m/s for throws of 83.84–89.52 m; release angle 27.7–40.1° (theoretical optimum cited as 32–37°); attack angle −6.8° to +8.8° (Hubbard & Alway's simulation optimum 0–2.5° for 23–35 m/s); release height 1.80–2.14 m; horizontal velocity component 21.54–25.88 m/s and vertical 13.61–18.14 m/s — [Campos et al. PDF](https://www.uv.es/jcampos/Documentos/NEA_IAAF_MenJavelin.pdf)
- Timing of the chain (same study): mean time from peak hip speed to release 130 ms (SD 10), from peak shoulder speed 90 ms (SD 20), from peak elbow speed 60 ms (SD 10); preparatory phase (t1–t2) 140–260 ms, final phase (t2–t3, front-foot plant to release) 100–140 ms — [Campos et al. PDF](https://www.uv.es/jcampos/Documentos/NEA_IAAF_MenJavelin.pdf)
- Block ("pressure") leg knee angle (same study): 158–178° at plant (t2) and 137–173° at release (t3); stated coaching principle: keep 160–180° with greatest extension at release; a thrower whose knee flexed progressively to 137° at release is described as losing support. Cited from Morriss & Bartlett: in elite throwers 60% of the javelin's kinetic energy is generated in the last 50 ms before release — [Campos et al. PDF](https://www.uv.es/jcampos/Documentos/NEA_IAAF_MenJavelin.pdf)
- Morriss, Bartlett, Navarro & Viitasalo, "The Biomechanics of Elite Javelin Throwing Technique" (ISBS proceedings; men's final, 1994 European Championships, 12 athletes, 3D cine): at final foot strike hips ≈ perpendicular to throw direction and shoulders rotated ≈ 50° further back; kinetic energy peaks earlier in proximal and later in distal segments; throwers who reduced body centre-of-mass horizontal velocity most between final foot strike and release threw furthest (r = 0.60, p = 0.039); lead-leg knee flexion during that period correlated inversely with distance (r = −0.59, p = 0.044); throwing-elbow angle at final foot strike ranged 149° (gold) to 118°; peak shoulder angular velocities 17.4 and 15.0 rad/s (gold, bronze), bronze-medallist peak elbow extension 29 rad/s (gold value illegible in the scan); estimated lateral grip forces 58 N (gold) vs 148 N (bronze) — [Morriss et al., ISBS](https://ojs.ub.uni-konstanz.de/cpa/article/view/2951/2798)
- Run-up speed is only about 5–6 m/s versus 28–30 m/s release, so most of the release speed is generated in the final two steps; a braced, nearly straight front leg lets the trunk rotate over it (popular-science summary by a biomechanist) — [The Conversation](https://theconversation.com/science-of-the-spear-biomechanics-of-a-javelin-throw-29782)
- Sequence is not strictly proximal-to-distal in the arm: one elite analysis found shoulder abduction, elbow extension and shoulder internal rotation grouped together after trunk rotation/tilt, with wrist flexion last (search-level) — [ISBS proceedings](https://ojs.ub.uni-konstanz.de/cpa/article/view/2702/2545)

### Inferences
- For a 27 m/s ball with the reviewed ball/foot ratio range (1.06–1.65; values near 1.2 are typical when foot centre speed is used — my reading of the range, not a sourced figure), required foot speed is roughly 16–25 m/s; a procedural model should expose the restitution/"effective mass" assumption rather than hide it.
- Validation targets for a procedural kick: thigh peak ≈ 500–600 deg/s *before* shank peak ≈ 1100–1900 deg/s; hip flexion torque ≈ 2× knee extension torque (≈ 200–300 vs 70–160 N·m); impact < 10 ms; support-leg vertical GRF ≈ 1.5–2 body weights; support knee 26° → 42° flexion; trunk back-lean ≈ 12–17°; pelvis rotation ≈ 30–36°; approach 3–4 m/s at ≈ 45°.
- Important modelling caveat for an "outcome-targeted torque drive": in real kicks the knee extensor *torque* is near zero or negative at impact; foot speed at impact comes from the whip (thigh deceleration, hip lift from the support leg). A drive that scales knee torque up to hit a ball speed will produce the right number with the wrong mechanics; a better abstraction drives the proximal joint and lets interaction torques do the rest, or at least checks the proximal-to-distal ordering of peaks.
- The plant/block leg does the same job in both skills — it converts approach momentum into rotation of proximal segments by braking the body (kick: 4–6 N/kg braking GRF; javelin: r = 0.60 between CoM deceleration and distance, r = −0.59 for knee flexion). "Plant" deserves to be a first-class intent with a stiffness/flexion budget and a braking-impulse outcome, not just a foot position.
- Javelin timing (130 / 90 / 60 ms before release, final phase 100–140 ms) gives concrete delays for a sequenced multi-joint drive.

### Gaps
- Linear foot speed at impact (m/s) for the instep kick was not found as a sourced value in the texts I read; only ratios and angular velocities.
- Javelin joint torques were not found; only kinematics and energy-flow statements. Bartlett's own review papers (J Sports Sci) were not retrieved; values come from Morriss/Bartlett co-authored proceedings and Campos et al.
- The gold-medallist elbow angular velocity in Morriss et al. is illegible in the scanned text; a search summary of another paper gave 56.3 rad/s for a gold medallist's peak elbow angular velocity, much higher than the 29 rad/s above — the studies disagree, probably through filtering/method differences ([ISBS search-level source](https://ojs.ub.uni-konstanz.de/cpa/article/view/5612/5106)).
- Shan & Zhang's 2011 full-body kick review (PMC3224572) was blocked by a verification page and Augustus et al.'s recent whole-body energy-transfer work was unreachable; modern (post-2015) whole-body power-flow numbers are therefore missing.
- Putnam's (1991/1993) summation-of-speed papers were not read directly; they are represented via the two reviews.
- All kicking data are 3D human data; no 2D-specific or sagittal-plane-reduced reference set was found.

## 6. Design lessons: what makes a motion-authoring abstraction robust and reusable

### Takeaway
Across 30 years the abstractions that lasted share four properties: **intent is separated from actuation** (targets/virtual forces/goals, not torques or poses), **skills carry explicit contracts and typed outcomes** (pre/post-conditions, success/failure, feedback), **parameters are body-relative and outcome-toleranced** so they retarget, and **unspecified aspects are filled by defaults or a prior** rather than required from the author.

### Cited Findings
- Separation of intent from actuation: SIMBICON states are target poses that need not be reached, with balance added by feedback on the swing hip; Coros et al. 2010 express walking through foot-placement targets and Jacobian-transpose virtual forces and need no character-specific tuning — [SIMBICON](https://www.cs.ubc.ca/~van/papers/2007-siggraph-simbicon.pdf); [Generalized Biped Walking Control](https://www.cs.ubc.ca/~van/papers/2010-TOG-gbwc)
- Explicit contracts enable composition: any controller that can answer "can you handle this state?" and "have you failed?" can join the pool; designers supply pre-conditions, post-conditions and expected performance, which the authors call "a fair and necessary price to pay" for composability; pre-conditions can be learned by sampling when hand-specification is hard — [Faloutsos et al. 2001](https://www.cs.ubc.ca/~van/papers/2001-siggraph-composable.pdf)
- Early, explicit failure paths: failure = inability to meet post-conditions, to be detected as early as possible so that "another more appropriate controller can take over"; control graphs include dedicated stand-up skills; StateTree routes Succeeded and Failed completions to different transitions; BTs provide Fallback nodes and per-tick re-evaluation — [Faloutsos et al. 2001](https://www.cs.ubc.ca/~van/papers/2001-siggraph-composable.pdf); [Liu et al. 2016](https://www.cs.ubc.ca/~van/papers/2016-TOG-controlGraphs/2016-TOG-controlGraphs.pdf); [Epic StateTree overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-state-tree-in-unreal-engine); [Colledanchise & Ögren](https://arxiv.org/pdf/1709.00084)
- Robustness should be measured, not asserted: Liu et al. report, per skill, the maximal recoverable 0.1 s trunk push found by increasing force in 10 N steps — [Liu et al. 2016](https://www.cs.ubc.ca/~van/papers/2016-TOG-controlGraphs/2016-TOG-controlGraphs.pdf)
- Feedback to the author/planner as part of the language: BML's prediction/progress/warning feedback and sync points; Text2Reward's iterative human feedback on generated rewards; RDA's finding that statistic-only reflection yields misaligned behaviour — [BML 1.0](https://projects.cs.ru.is/projects/behavior-markup-language/wiki); [Text2Reward](https://arxiv.org/pdf/2309.11489); [RDA](https://arxiv.org/html/2606.01672v1)
- Manner separate from goal: spacetime constraints' what/how; EMOTE's Effort/Shape parameters applied over independently defined movements — [Witkin & Kass](https://history.siggraph.org/?p=119573); [EMOTE](https://www.cis.upenn.edu/~badler/siggraph00/emote.pdf)
- Sparse specification with completion: MaskedMimic accepts any subset of constraints and inpaints the rest; Cascadeur exposes weights for how strongly authored keys are preserved versus physically corrected — [MaskedMimic](https://research.nvidia.com/labs/par/maskedmimic/); [Cascadeur AutoPhysics settings](https://cascadeur.com/help/tools/physics_tools/autophysics/autophysics_settings)
- Retargeting across bodies: Coros et al. 2010 run one controller across characters without per-character tuning; SMPLOlympics standardises on SMPL/SMPL-X-compatible humanoids so human data transfers; biomechanics reports body-size-normalised quantities (GRF in N/kg, support-leg moments in N·m/kg) — [Generalized Biped Walking Control](https://www.cs.ubc.ca/~van/papers/2010-TOG-gbwc); [SMPLOlympics](https://arxiv.org/html/2407.00187); [Lees et al. 2010](https://numerik.mi.fu-berlin.de/wiki/WS_2020/CoMaI_Dokumente/FTVS-2332-version1-the_biomechanics_of_kicking_in_soccer_a_review.pdf)
- Contact as the stable intermediate vocabulary: UniHSI's joint↔object-part contact chains for LLM plans; Cascadeur's per-interval fulcrum points; SIMBICON's contact-triggered transitions — [UniHSI](https://arxiv.org/html/2309.07918v5); [Cascadeur Fulcrum Points](https://cascadeur.com/help/tools/physics_tools/fulcrum_points); [SIMBICON](https://www.cs.ubc.ca/~van/papers/2007-siggraph-simbicon.pdf)
- Composition vocabulary for generator scripts: `all`, `any`, `chain`, `delay`, `sequence`, `loop` and `yield*` delegation — [Motion Canvas flow docs](https://motioncanvas.io/docs/flow)
- LLM-facing APIs are bounded by their primitives and observability: Code as Policies is limited by available perception APIs and control primitives and degrades on instructions much more complex than its examples; 2026 planners constrain the model to a typed skill library and validate each call — [Code as Policies](https://arxiv.org/abs/2209.07753); [Physical Agentic AI](https://arxiv.org/html/2608.22657v1)

### Inferences
Concrete recommendations for the generator-"story" library, each traceable to the findings above:
1. **Give every intent and every story a typed result** (`succeeded | failed(reason, margin) | interrupted`) and let `yield` return it; add a per-step *expected-performance* guard evaluated every simulation tick (not only at yields) that can abort the story into a fallback (Faloutsos; StateTree; BT Fallback).
2. **Make every wait a race with a timeout** by default — `any(event, timeout)` — and define what happens when the awaited event has already occurred on entry (SIMBICON's skip rule).
3. **Declare pre-/post-conditions per story** in the same predicate vocabulary used for waits (balance over support, contact states, velocity regions), so stories can be chained, checked, and later sampled to learn feasibility regions.
4. **Adopt BML-style named sync points** on long intents (ready / stroke / relax) and Motion Canvas' combinator names for concurrency; use `yield*` for sub-stories.
5. **State outcomes as target ± tolerance and report signed margins and minimal relaxations** when unmet (DeepMimic tolerance; STL robustness and relaxation).
6. **Keep "what" and "how" separate**: placements/outcomes vs effort/style/settle parameters (spacetime constraints; EMOTE).
7. **Use body-relative, normalised parameters** (leg lengths, body weights, N·m/kg; anchors named relative to objects such as "beside the ball") for retargeting, and treat *contacts* (which body part, on what, when) as first-class named entities.
8. **Encode the kinetic chain as a sequenced proximal-to-distal drive with a braking plant**, and validate against the reference values in §5 rather than hitting the outcome with a single distal torque.
9. **Provide defaults for everything unspecified** so sparse LLM-written scripts remain valid (MaskedMimic's lesson), and return execution traces/feedback that an LLM can read to revise the script (Text2Reward, RDA).

### Gaps
- No published empirical comparison was found of generator/coroutine scripts versus FSMs or behaviour trees *for physically simulated characters*; the argument for generators rests on game-scripting practice and on equivalence to phase FSMs, not on a study.
- No source was found that evaluates how well LLMs author against such an API (success rates by API design); the Code-as-Policies limits are the nearest evidence.
- Retargeting of *scripted procedural* controllers across body proportions in 2D specifically is not covered by any source I found.
